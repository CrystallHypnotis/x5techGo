# Интерфейсы в Go — разбор примеров

В каждом каталоге находится отдельная программа. Запускать её можно из соответствующей папки командой `go run .` (если в ней есть `go.mod`) или `go run main.go`. Пример `02-concrete` намеренно содержит несовместимый вызов и не компилируется; в `04-method-set` также оставлена строка, демонстрирующая ошибку присваивания.

## 01-methods — методы и получатель-копия

**Алгоритм.** Создаётся значение `Email`, печатается его адрес через `Label`, затем вызывается `Rename`, после чего адрес печатается снова. Поскольку метод `Rename` имеет получатель-значение, он меняет копию `Email`, а исходное значение остаётся прежним.

**Синтаксис.** `func (e Email) Label() string` объявляет метод типа `Email`; выражение в скобках перед именем метода — получатель. `Email{Address: ...}` создаёт структуру с указанным полем. Чтобы метод менял исходную структуру, обычно используют указатель-получатель: `func (e *Email) Rename(...)`.

**Результат.** Оба вывода содержат `old@example.com`.

## 02-concrete — ограничение конкретного типа

**Алгоритм.** `NotifyEmail` принимает только `Email` и вызывает его метод `Send`. В `main` сначала передаётся `Email`, а затем предпринимается попытка передать `Push`.

**Синтаксис.** Методы `Send` у `Email` и `Push` имеют одинаковую форму, но это не создаёт отношения подтипов между структурами. Параметр `n Email` требует значение ровно типа `Email`; Go не выбирает аргумент только по совпадению методов.

**Важно.** Программа намеренно не компилируется на строке `NotifyEmail(Push{}, ...)`: тип `Push` нельзя передать вместо `Email`. Дальше в уроке показано решение через интерфейс.

## 03-interface — неявная реализация интерфейса

**Алгоритм.** `Notify` принимает любое значение, способное отправить сообщение и предоставить адрес. В примере ему передаются `Email` и `Push`; конкретный метод `Send` выбирается по фактическому типу значения.

**Синтаксис.** `type Notifier interface { Send(string); GetAddress() string }` задаёт набор методов. Тип реализует интерфейс неявно: отдельное объявление `implements` не нужно. Методы-проверки `var _ Notifier = Email{}` и `var _ Notifier = Push{}` заставляют компилятор проверить соответствие типов интерфейсу. `SMS` тоже реализует `Notifier`, потому что у него есть оба метода, хотя в `main` он не используется.

**Нюанс.** Функция `Notify` вызывает только `Send`, но для передачи значения всё равно необходимо реализовать все методы интерфейса `Notifier`, включая `GetAddress`.

## 04-method-set — набор методов и указатель-получатель

**Алгоритм.** `Counter.Send` увеличивает счётчик. Сначала метод вызывается на переменной `c`, затем через интерфейс, в который помещён `&c`; в конце показана попытка поместить в интерфейс само значение `c`.

**Синтаксис.** Метод `func (c *Counter) Send(string)` имеет получатель-указатель. Набор методов `*Counter` включает методы с получателем `*Counter` и `Counter`, а набор методов `Counter` включает только методы с получателем `Counter`. Поэтому `*Counter` удовлетворяет `Notifier`, а `Counter` — нет. Проверка `var _ Notifier = (*Counter)(nil)` компилируется: это compile-time assertion, значение не вызывается.

**Важно.** Go автоматически берёт адрес переменной при прямом вызове `c.Send(...)`, если `c` адресуем. Это удобство вызова не меняет набор методов типа при проверке совместимости с интерфейсом. Строка `var bad Notifier = c` намеренно вызывает ошибку компиляции; закомментируйте её, чтобы запустить программу. После двух успешных вызовов счётчик равен `2`.

## 05-dispatch — динамическая диспетчеризация

**Алгоритм.** В `main` собирается срез отправителей, после чего `Dispatch` по очереди отправляет каждому одно сообщение. Если метод вернёт ошибку, цикл немедленно завершится и вернёт её; если ошибок нет — вернётся `nil`.

**Синтаксис.** `[]Notifier` — срез интерфейсных значений. Элементы разных конкретных типов (`Email`, `Push`, `Console`) можно хранить вместе, потому что каждый реализует `Send(string) error`. В `for _, n := range all` `_` отбрасывает индекс. `if err := n.Send(message); err != nil` — короткое объявление переменной в условии; `return err` прерывает обработку.

**Результат.** Все три отправителя печатают сообщение, затем выводится `ошибка: <nil>`.

## 06-embedding — встраивание структуры и продвижение методов

**Алгоритм.** `Email` содержит встроенное поле `Base`. Вызов `e.Log` использует продвинутый метод `Base.Log`, а `e.Name` — метод `Email.Name`, который затеняет продвинутый `Base.Name`. `e.Report()` выполняет метод `Base.Report`, внутри которого вызывается `b.Name()` на получателе типа `Base`.

**Синтаксис.** Поле `Base` объявлено без имени поля: `type Email struct { Base; Address string }`. Это встраивание (embedding), а не наследование. Методы встроенного поля можно вызывать через внешний тип, если имя не конфликтует. Явная запись `e.Base.Log(...)` обращается непосредственно к встроенному полю. Внутри `Base.Report` получатель `b` остаётся `Base`, поэтому вызов `b.Name()` не становится виртуальным вызовом `Email.Name`.

**Результат.** `e.Name()` возвращает `email`, а `e.Report()` печатает `Report: base`.

## 07-type-switch — type switch для значения `any`

**Алгоритм.** `Describe` проверяет динамический тип переданного значения и возвращает описание. Цикл передаёт значения `Email`, `*Email`, `Push`, числа, строки и `nil`, печатая описание каждого.

**Синтаксис.** `any` — псевдоним пустого интерфейса `interface{}`; он может хранить значение любого типа. Конструкция `switch v := value.(type)` допустима только для type switch и связывает `v` с динамическим значением. В ветках `case Email` и `case *Email` переменная `v` имеет соответствующий тип. `case nil` обрабатывает интерфейс, у которого нет динамического значения; `default` ловит остальные типы. Проверка `v == nil` в ветке `*Email` нужна отдельно: интерфейс может содержать nil-указатель.

## 08-interface-embedding — объединение интерфейсов

**Алгоритм.** `Show` принимает значение, умеющее и сообщать своё имя, и отправлять сообщение. `Console` реализует оба метода, поэтому программа печатает имя и отправляет сообщение.

**Синтаксис.** `NamedSender` встраивает интерфейсы `Sender` и `Named`; его набор методов — объединение требований этих интерфейсов. Чтобы удовлетворять `NamedSender`, тип должен реализовать `Send(string)` и `Name() string`. Интерфейсы в Go структурно типизированы: реализация определяется набором методов, а не явным объявлением.

## 09-assertion — проверка динамического типа

**Алгоритм.** Для каждого значения `Notifier` программа пробует получить `*Email`. Пара `e, ok` показывает результат проверки: при совпадении `ok == true` и `e` содержит указатель, иначе `ok == false` и `e == nil`. Затем проверяется утверждение к анонимному интерфейсу с тем же методом `Send`.

**Синтаксис.** `n.(*Email)` — утверждение типа (type assertion), применяемое к интерфейсу. Форма с двумя результатами `value, ok := ...` безопасно сообщает о несовпадении; форма с одним результатом вызвала бы panic при несовпадении. Анонимный интерфейс `interface { Send(string) }` задаёт требование прямо в выражении. В данном случае проверка истинна для всех значений `Notifier`, потому что именно этот метод и определяет `Notifier`.

## 10-nil-interface — интерфейс с nil-указателем

**Алгоритм.** Сначала `n` — полностью nil-интерфейс. Затем в него записывается nil-указатель `p` типа `*Email`; интерфейс после этого уже не равен `nil`. Вызов метода допустим, и метод сам проверяет nil-получатель.

**Синтаксис и модель.** Интерфейсное значение концептуально хранит пару `(динамический тип, динамическое значение)`. У пустого интерфейса оба отсутствуют, поэтому `n == nil` истинно. После `n = p` пара — `(*Email, nil)`, поэтому сам интерфейс не nil, хотя `p == nil`. `%T` печатает динамический тип. Получатель `e *Email` может быть nil; проверка `if e == nil` защищает доступ к полю.

**Практический вывод.** При возврате указателя из функции в интерфейс важно не возвращать типизированный nil как будто это nil-интерфейс. Если требуется обозначить отсутствие значения, возвращайте сам nil-интерфейс.
